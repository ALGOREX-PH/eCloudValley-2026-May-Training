Module 04 · 45 minutes

RAG Fundamentals

Retrieval-Augmented Generation: the unglamorous workhorse of useful AI.

"Module 4. RAG. Retrieval-Augmented Generation. The least sexy term in modern AI. Also the technique behind almost every production AI feature you've actually used. Quick theory, then we build."

Why RAG?

  • Hallucination. The model makes things up confidently.
  • Freshness. Training data has a cutoff. Your data changes daily.
  • Privacy. Your internal docs aren't in any model's training set — and shouldn't be.
  • Cost. Smaller context = fewer tokens = cheaper inference.
RAG = "look it up before you answer."
"Four reasons RAG exists. Memorize the first three, the fourth is just a bonus." "Hallucination is the killer. Production AI projects die because someone shipped a model that confidently lies, then a customer screenshots it, then it's on Twitter. RAG doesn't eliminate hallucination — but it cuts it down enormously when the model can ground its answer in actual retrieved text." "Privacy — your internal data doesn't go into the model's weights. Period. RAG keeps it in a database you control. That's also a regulatory answer when compliance asks where the data lives."

The vanilla RAG pipeline

   ┌──────────────────────────────────┐         ┌──────────────────────────┐
   │ INDEX (one-time, batch)           │         │ QUERY (every request)     │
   │                                  │         │                          │
   │  raw docs                        │         │  user question           │
   │     ↓ chunk                      │         │     ↓ embed              │
   │  chunks                          │         │  query vector            │
   │     ↓ embed                      │         │     ↓ similarity search  │
   │  vectors → vector DB             │         │  top-k chunks            │
   │                                  │         │     ↓ stuff into prompt  │
   │                                  │         │  LLM → answer            │
   └──────────────────────────────────┘         └──────────────────────────┘
"Two halves. Read them as two completely separate programs that share a database. Index runs once, in batch, when your docs change. Query runs on every user request, has to be fast." "People who put the embedding step inside their request handler get embarrassed in code review. Don't be that person. Index ahead of time. Query at runtime. Different code paths, different SLAs."

Embeddings, made small

An embedding is a list of numbers that captures the meaning of a piece of text. Closer vectors = closer meanings.


client.embeddings.create(
    model="text-embedding-3-small",
    input="The quick brown fox",
)
# → [0.0123, -0.045, 0.78, ..., 0.012]   (1536 numbers)
    
   "puppy"   ─┐                         ─┐
              │   ─── close             │  cosine ≈ 0.92
   "dog"     ─┘                         ─┘

   "puppy"   ─┐                         ─┐
              │   ─── far               │  cosine ≈ 0.13
   "tax law" ─┘                         ─┘
"Embeddings. A list of numbers that captures meaning. Don't overthink it. The model has decided that 'puppy' and 'dog' are close in meaning-space. We trust it." "1536 numbers for `text-embedding-3-small`. Cheap, fast, good enough for 90% of use cases. OpenAI also has `-3-large` at 3072 dims if you need precision and you're willing to pay for it. Start small, upgrade only if eval scores tell you to."

Chunking: the unglamorous decision that makes or breaks you

StrategyHowWhen
Fixed-sizeEvery N tokens, with overlapDefault. Simple, works fine.
RecursiveSplit on \n\n, then \n, then . until small enoughMost production systems.
SemanticEmbed sentences, group by similarityLong-form docs. Slower to index.
Markdown / structuralSplit on headings, keep parents in metadataDocs with hierarchy (manuals, handbooks).
Rule of thumb: 500–1000 tokens per chunk, 50–100 token overlap. Then iterate based on eval results.
"This slide is the most under-rated thing in this whole training. Chunking. The entire quality of your RAG system gets decided here, before any model is involved." "I've watched teams tune prompts for two weeks when they should've tuned chunk size for thirty seconds. Chunks too small — you fragment ideas, retrieve gibberish. Chunks too big — you bury the relevant sentence in a wall of noise." "Start with the rule of thumb. 500 to 1000 tokens, 50 to 100 overlap. Ship it. Then let your eval set tell you whether to go up or down. Don't guess."

Chroma is the right tool for a workshop. In production, your data plane usually picks for you.

"Five options, one decision. Tonight we use Chroma — it's the fastest path from zero to working RAG, runs in-process, persists to a local folder." "In production, the answer is almost never Chroma. It's whatever your data team already runs. Postgres shop? pgvector. AWS shop? OpenSearch. Greenfield startup with budget? Pinecone or Qdrant. The 'best' vector DB is the one your ops team won't fight you on." Beat. "Don't pick a vector DB on Twitter recommendations. Pick the one that matches your existing data plane. The agentic part of your system doesn't care which one you chose."

Retrieval flavors

Dense (semantic)

Cosine similarity on embeddings. Good at synonyms, paraphrases.

Sparse (BM25 / lexical)

Keyword matching. Good at acronyms, IDs, exact terms.

Hybrid

Run both, merge with reciprocal-rank-fusion. Almost always wins in eval.

Re-ranking

Retrieve 50, re-rank with a cross-encoder to top 5. Slow but precise.

Start dense. Add hybrid when "exact match" queries fail. Add re-ranking last.
"Four ways to find stuff. People treat them as a hierarchy where re-ranking is 'the best.' That's not how it works. They have different jobs." "Dense is great at meaning — 'how do I rotate keys' finds 'API key rotation procedure' even with no shared words. Sparse is great at exact terms — invoice IDs, error codes, SKU numbers." "Hybrid combines both. Almost always beats either one alone in eval. Re-ranking is the expensive precision pass — retrieve 50 candidates with hybrid, re-rank to the best 5 with a cross-encoder. Slow. Good. Use last." "The order matters. Dense first, hybrid when exact-match queries start failing, re-rank when precision is your bottleneck. Don't add re-ranking because a blog post said to."

Agno's Knowledge — RAG without the plumbing


from agno.knowledge import Knowledge
from agno.vectordb.chroma import ChromaDb

knowledge = Knowledge(
    vector_db=ChromaDb(
        collection="cloudkaiju-docs",
        path="chroma_db",
    ),
)

# One-time: ingest a folder of PDFs / MD / text files
knowledge.add_content(path="docs/")

# Now you can query directly...
results = knowledge.search("How do I rotate API keys?", num_documents=5)
for r in results:
    print(r.content[:200], r.metadata)
"Six lines of meaningful code. Knowledge object, vector DB, ingest, search. That's a working RAG pipeline." "The hard part isn't this code. The hard part is what you put in `docs/`. Garbage docs, garbage retrieval. The model can't fix bad source material. Treat your docs folder like production data — clean it, version it, own it."

Module 05 · 50 minutes

Agentic RAG

When the agent decides whether, what, and how to retrieve.

"Module 5. We take vanilla RAG and we make the agent the boss of it. The agent decides if it needs to retrieve. It rewrites the query. It loops if one search wasn't enough. This is where RAG starts feeling intelligent instead of mechanical."

Vanilla RAG vs Agentic RAG

Vanilla RAGAgentic RAG
RetrievalAlways, on every queryOnly when the agent thinks it's needed
QueryThe user's raw questionRewritten by the agent for better recall
Multi-stepOne retrieval per requestIterative — retrieve, think, retrieve again
Failure mode"I don't know" or hallucinationAgent reflects, tries different angle
"Read across the rows. Each row is an upgrade. The cost is more LLM calls — every retrieval decision is a model call, every rewrite is a model call. The benefit is the agent stops being dumb." "Vanilla RAG retrieves on every query. User says 'hi'? It retrieves. Wasteful and sometimes embarrassing — the answer ends up grounded in some random doc. Agentic RAG asks the question first: do I actually need to look this up? Smart agents skip retrieval when they don't. Smarter agents rewrite the query before searching. We're building the second kind."

The "knowledge as a tool" pattern


agent = Agent(
    model=OpenAIChat(id="gpt-4o-mini"),
    knowledge=knowledge,
    search_knowledge=True,   # 👈 the magic flag
    instructions=[
        "Use the knowledge base to answer questions about CloudKaiju.",
        "Always cite source: [filename, page #].",
        "If the answer isn't in the docs, say so explicitly.",
    ],
    show_tool_calls=True,
)

Behind the scenes: search_knowledge=True registers a search_knowledge_base tool. The agent calls it when (and only when) it judges it needed.

"One flag. `search_knowledge=True`. That's the line that turns yesterday's chatbot into an agentic RAG system. Conceptually huge. Technically: one bool." "The rest is instructions. Read those carefully — they're the contract. 'Always cite source.' 'If not in the docs, say so explicitly.' The model will follow these if you state them cleanly. Vague instructions, vague behavior. Specific instructions, specific behavior."

Query rewriting

Users ask short questions. Vector search wants specific queries. The agent rewrites:


User:   "what about the keys"

Agent's rewrite:   "API key rotation procedure CloudKaiju"

→ much better hit on the docs
Agno does this for you when search_knowledge=True. You can also drive it explicitly with a custom search tool.
"Users type like users. Vector search wants engineering team English. The agent in the middle bridges the gap." "'What about the keys' becomes 'API key rotation procedure'. That's a 10× retrieval improvement for free. You did not write the rewriter. The model is the rewriter. This is the part where 'agentic' starts paying for itself."

Multi-step retrieval

   User:  "Which features were added between v2 and v3?"

   Agent: → search_knowledge("CloudKaiju v2 changelog")
          ← results: [v2.0, v2.1, v2.2 features]
   Agent: → search_knowledge("CloudKaiju v3 changelog")
          ← results: [v3.0, v3.1 features]
   Agent: I now have both. Compute the diff:
          → "Added in v3: X, Y, Z. Removed: W. Cited: [...]"

No code change needed — the agent loops on its own, deciding when to stop.

"Watch the trace. Two retrievals, then synthesis. The agent decided to do two searches because one wouldn't have answered the question. It also decided when to stop. You did not write that loop. The model wrote that loop." "This is the moment people get giddy about agents — and they should. But remember Module 1 from yesterday: earn the agent. If your use case is one-shot Q&A, don't bolt this on. If your use case actually needs comparison, decomposition, multi-step reasoning — this is the win."

    ],
)
"Every line in this `instructions` list was paid for in production tears. Mine and other people's. Let me walk through them." "Citations — because users don't trust uncited AI output, and they shouldn't. Refuse off-topic — because someone will ask your customer support agent to write a poem about their ex and screenshot it for Twitter. Never invent — because the lawyers care, and so should you. Account ID before customer data — because your security team really cares." Beat. "Each line is a scar. You'll add your own scars as you ship."

Common failure modes

SymptomFix
Wrong / outdated answerRe-index. Check the chunk metadata for stale doc.
"I don't know" when info is in docsBad chunking, or query needs rewriting. Check what was retrieved.
Cites wrong sourceChunks too big — multiple topics in one chunk. Reduce size.
Loops calling search foreverSet tool_call_limit=5. Add "stop after 3 searches" to instructions.
Slow first responseRe-ranking is expensive. Cache or skip on common queries.
"Five bugs you'll meet. The first three are chunking problems wearing different masks — when retrieval feels broken, look at chunking before you look at the model." "The fourth is the scary one. Set `tool_call_limit`. Always. Same as yesterday — I'm not paying your OpenAI bill, and infinite tool loops at 3 cents a call add up faster than you'd think." "The fifth is a UX issue, fix with caching."

Wrap an agent in FastAPI


from fastapi import FastAPI
from pydantic import BaseModel
from agno.agent import Agent
from agno.models.openai import OpenAIChat

app = Agent(
    model=OpenAIChat(id="gpt-4o-mini"),
    knowledge=knowledge,
    search_knowledge=True,
)

api = FastAPI()

class Ask(BaseModel):
    question: str
    session_id: str | None = None

@api.post("/ask")
def ask(payload: Ask):
    result = app.run(payload.question, session_id=payload.session_id)
    return {"answer": result.content, "session_id": result.session_id}
"FastAPI. Pydantic schema for the input. One POST endpoint. That's the entire web layer." "If you've shipped any Python API in the last five years, this is muscle memory. The agent becomes just another dependency in your FastAPI app. No special framework, no agent-specific runtime, just a function call inside a route handler."

Connecting to your data platform

Most enterprise data lives in S3, Snowflake, Postgres, or BigQuery. Expose them as tools.


@tool
def query_orders(customer_id: str, days: int = 30) -> list[dict]:
    """List a customer's orders in the past N days. Use for support questions."""
    rows = pg.execute(
        "SELECT * FROM orders WHERE customer_id=%s AND created_at > now() - %s",
        (customer_id, f"{days} days"),
    ).fetchall()
    return [dict(r) for r in rows][:50]   # always cap!

agent = Agent(
    model=OpenAIChat(id="gpt-4o-mini"),
    tools=[query_orders, query_invoices, query_tickets],
    instructions="You are a customer support agent. Use tools to look things up.",
)
Cap row counts. A LIMIT-less SELECT is how agents melt your data warehouse.
"The other half of production agents. RAG handles unstructured docs. Tools handle structured data. The pattern: every meaningful table or warehouse view becomes a tool." "Look at line 8. CAP THE ROW COUNT. I cannot stress this enough. An agent calling a tool without a LIMIT clause has melted more Snowflake bills than I'd like to admit. Always cap. The model can ask for more if it needs more, but the default is bounded."

Evaluation: do you actually know it works?


# A minimal eval set
EVAL_CASES = [
    {"q": "How do I rotate API keys?",       "must_cite": "security.md"},
    {"q": "What's the SLA on Pro tier?",     "must_cite": "pricing.md"},
    {"q": "What's the weather?",             "must_refuse": True},
]

def eval_agent(agent, cases):
    pass_, fail_ = 0, 0
    for c in cases:
        result = agent.run(c["q"])
        ok = (
            (c.get("must_cite") in result.content if c.get("must_cite") else True)
            and (("don't" in result.content.lower() or "can't" in result.content.lower())
                 if c.get("must_refuse") else True)
        )
        pass_ += ok; fail_ += not ok
    return pass_, fail_
Run this on every PR. Without it, you're flying blind.
"Eval set. Twenty cases minimum. Run on every pull request, gate the merge on it." "This is the unsexy thing that turns 'we built an AI feature' into 'we own an AI product.' Without evals, your model upgrades are vibes. Someone bumps gpt-4o-mini to gpt-4o-something-new, stuff breaks silently, you find out from a customer two weeks later. With evals, the upgrade either passes or fails before it ships." Beat. "If your team builds anything serious with agents, the eval suite is more important than the agent."
