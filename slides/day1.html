Module 01 · 35 minutes

Fundamentals of Agentic AI

What's an agent, really? When should you build one — and when shouldn't you?

"Module one. Theory. I'll keep it short. The whole point of this section is so that when you read 'agentic' on LinkedIn next week, you know whether it's real or marketing."

The least controversial definition

An agent is an LLM in a loop, deciding what to do next based on what it sees.

That's it. The rest is engineering.

"There are a hundred definitions of 'agent' on the internet. Most of them are someone selling something. This one's from Anthropic's 'Building Effective Agents' paper, and it's the cleanest. LLM. In a loop. Deciding. Based on what it sees. Four ideas. Memorize that, you can debate anybody on Twitter and win." Pause. "Everything else — the frameworks, the patterns, the buzzwords — is engineering on top of that loop."

LLM call vs Chatbot vs Agent

LLM call

Stateless. One in, one out.


client.responses.create(
  model="gpt-4o",
  input="Hi"
)

Chatbot

Stateful conversation.
No outside actions.


agent.run("Hi")
agent.run("What did I just say?")
# remembers

Agent

Picks tools.
Loops.
Acts on the world.


agent = Agent(
  tools=[search, calc],
  ...)
agent.run("Find & sum X")
"Three things people confuse on a daily basis. LLM call — fire and forget. Chatbot — has a memory of the chat, that's it. Agent — picks tools, takes actions, loops until it's done. ChatGPT in 2022 was a chatbot. ChatGPT today, with browsing and code, is an agent. Same model under the hood. The difference is the loop and the tools. Everything you build tonight, you'll build by walking left to right across this slide."

The four properties of an agent

1. Autonomy

Decides its own next step.

2. Tools

Can act on the world (search, query, write).

3. Memory

Recalls earlier turns & persistent facts.

4. Reasoning

Plans, reflects, recovers from errors.

"Four. Autonomy, tools, memory, reasoning. If your system has all four to some degree, it's agentic. If it has only the first two and follows a fixed script, it's a workflow. The line is fuzzy on purpose — anyone who tells you there's a hard boundary is selling a course." Beat. "Tonight: Module 2 covers memory. Module 3 covers tools. Reasoning happens for free as a side effect — the model is smart, it'll do most of the planning if you let it."

The spectrum: workflow → agent

        Fixed pipeline                                     Open-ended loop
        ─────────────────────────────────────────────────────────────
        Script  →  RAG  →  Workflow  →  Agentic RAG  →  Multi-Agent
        ─────────────────────────────────────────────────────────────
        Predictable, cheap                          Powerful, expensive
        Easy to test                                Hard to test
Pick the leftmost option that solves your problem. Don't lead with "agent."
"Read this left to right. Cheaper, more predictable, easier to test on the left. Sexier, more powerful, completely unhinged on the right." Pause for the laugh. "My rule: pick the leftmost option that solves your problem. If a script works, ship the script. If RAG works, ship RAG. Don't reach for multi-agent because it sounds cool on a pitch deck. I've audited too many systems where someone built a five-agent constellation when a single function call would've done it. They look impressive in demos. They die in production."

Pattern: ReAct (Reason + Act)

   ┌───────────────────────────────────────┐
   │  Thought:  I need to know X.          │
   │  Action:   search("X")                │
   │  Observ:   "X is ..."                 │
   │  Thought:  Now I can compute Y.       │
   │  Action:   calculator(...)            │
   │  Observ:   42                         │
   │  Thought:  I have the answer.         │
   │  Final:    "Y is 42"                  │
   └───────────────────────────────────────┘

Yao et al., 2022 — every modern agent uses some flavor of this.

"ReAct. Reason, Act, Observe. Repeat. Yao et al., 2022. Every framework you've heard of — LangGraph, OpenAI Agents, Agno — they all run some version of this loop under the hood. Different sugar, same recipe." "By Lab 3 you'll watch this trace stream past in your terminal. Once you see it, you can't unsee it."

Other patterns worth knowing

PatternWhenTrade-off
Plan-and-ExecuteMulti-step task with predictable structureBetter planning, more rigid
ReflexionAgent should self-correct after failureHigher quality, more tokens
Multi-agentDistinct roles or parallel workPowerful, very hard to debug
RoutingMany specialists, one entryClean separation, slight latency
"Don't memorize names. Memorize trade-offs. When someone on your team says 'let's do multi-agent', the next words out of your mouth should be 'how are we going to debug it?' If they look at you blank, you have your answer." "We're doing ReAct in Lab 3. It's the workhorse. Master it, the others are variations."

When NOT to use an agent

Don't

  • The flow is deterministic → use a workflow
  • You need millisecond latency
  • One LLM call already works
  • Safety-critical & can't tolerate hallucination

Do

  • Path branches based on intermediate results
  • You need tools to find the answer
  • The user's intent is open-ended
  • System should recover from its own errors
"Real talk. Most production wins from 'AI' in the last two years were not agents. They were a single well-prompted LLM call wrapped in a function. Don't be the engineer who built a five-tool agent to do regex. Earn the agent. The system tells you when it needs one." "If your boss says 'we need an agent for X' — your job is to ask whether X actually needs one. Half the time, no. Other half, yes, and now you know which half you're in."

Module 02 · 45 minutes

Building AI-Powered Chatbots

From a one-shot LLM call to a chatbot with persistent memory.

"Open your terminals. By the end of this module you'll have a chatbot that remembers your name across process restarts. Sounds simple. It's three concepts stacked on top of each other and most people get one of them wrong."

What is a chat completion, really?


messages = [
    {"role": "system",    "content": "You are a polite assistant."},
    {"role": "user",      "content": "Hi, my name is Danielle."},
    {"role": "assistant", "content": "Nice to meet you, Danielle!"},
    {"role": "user",      "content": "What's my name?"},
]

# The model sees the WHOLE list every call. There's no server-side memory.
response = client.responses.create(model="gpt-4o-mini", input=messages)

"Memory" in chatbots = sending the history back every time.

"Look at this carefully. The model has no memory. None. Zero. Every API call, you send the entire conversation back. That's the secret. ChatGPT 'remembering' you is just OpenAI keeping your messages on their side and prepending them. There's no magic." "Why does this matter? Because every turn costs tokens. Every turn. Long conversations get expensive fast. You'll feel that in Lab 2."

Knobs that matter

KnobWhat it doesDefault
temperatureRandomness. 0 = deterministic, 2 = wild1.0
max_tokensHard cap on response length~4096
systemPersistent persona / rules—
stream=TrueToken-by-token outputFalse
toolsFunctions the model may call—
For agents: temperature=0 for tool selection, ≥0.7 for creative output.
"Five knobs. Memorize three. Temperature, system, tools. The rest are tuning." "Temperature is the one people abuse. Default is 1.0 which is fine for chat. For agents picking tools — set it to zero. You don't want creativity in tool selection. You want the same input to produce the same tool call every time. Save the creativity for the writing, not the routing."

The chatbot problem


agent.run("Hi, I'm Danielle.")
agent.run("What's my name?")
# → "I don't know, you didn't tell me."  😩
Each run() is a fresh API call. The agent has no memory unless we give it some.
"Two lines. Should work. Doesn't. The model is acting like it has amnesia because it does. Every run is a fresh API call. We told it our name in call one and threw the receipt away. Call two starts from nothing." "This is the moment people freak out and reach for vector databases. Don't. We just need to send the history back. That's all 'memory' is at this layer."

Three flavors of memory

TypeWhat it storesLifetime
Conversation historyRecent turnsSingle session
Session storageThe full chat logAcross processes (DB)
User memoryDistilled facts about the userForever

Today we cover the first two. User memory is a Day 2 stretch goal.

"Three flavors. Don't conflate them. Conversation history is RAM — gone when the process dies. Session storage is disk — survives a restart. User memory is the agent quietly building a profile of you, like how good chat apps remember your preferences. Different tools for different jobs."

Adding history


agent = Agent(
    model=OpenAIChat(id="gpt-4o-mini"),
    add_history_to_messages=True,   # 👈 include past turns
    num_history_runs=10,             # 👈 how many to include
    instructions="You are a friendly assistant.",
)

agent.run("Hi, I'm Danielle.")
agent.run("What's my name?")
# → "Your name is Danielle." ✅

In-process only. Restart, lose it.

"Two flags. That's the whole fix for in-session memory. Set them, your agent remembers. `num_history_runs=10` means it sends the last ten turns. Crank that to 100 and watch your token bill cry. There's a real trade-off between context and cost — pick a number that matches your use case."

Persistent memory with SqliteStorage


from agno.agent import Agent
from agno.storage.sqlite import SqliteStorage
from agno.models.openai import OpenAIChat

storage = SqliteStorage(
    table_name="chat_sessions",
    db_file="agent_storage/chat.db",
)

agent = Agent(
    model=OpenAIChat(id="gpt-4o-mini"),
    storage=storage,
    session_id="user-42",       # same id = same chat
    add_history_to_messages=True,
)

Restart the process. Same session_id → picks up where it left off.

"SQLite. One file. Survives restarts. In production you'd swap this for Postgres but the interface is the same — `session_id` is your conversation key. Same id, same chat. Different id, different chat. That's also how you get multi-user — one session per user." "Common bug coming up in Lab 2: people forget to set `session_id` and every run gets a new UUID. Then they wonder why memory doesn't persist. Watch for that."

Module 03 · 55 minutes

Tools & Reasoning

Where chatbots become agents.

"Last module of the night. This is where it stops being a chatbot and starts being an agent. The difference is one line of code and a whole new class of bugs. Let's go."

What is a "tool"?

A tool is a Python function the LLM is allowed to call.
  • The model decides when, which, and with what args
  • Function signature + docstring → JSON schema → sent to the model
  • Model returns "call this with these args" → framework runs it → result fed back
"A tool is just a Python function. That's it. You write the function. The framework wraps it in a JSON schema. The model sees the schema and decides whether to call it. The framework runs the function and gives the model the result. Loop." "The model is not running your code — it's asking the framework to run your code on its behalf. That's an important distinction when you start worrying about security."

The function-calling loop

   You: "What's the weather in Manila and Tokyo? Sum the temps."

       ↓

   Agent: I should call get_weather twice and add.
   → tool_call: get_weather("Manila")
   ← result: 31°C
   → tool_call: get_weather("Tokyo")
   ← result: 18°C
   → tool_call: calculator("31 + 18")
   ← result: 49
   ← Final: "49°C combined."

This is ReAct, executed for you by Agno.

"Trace it with your eyes. The model could've tried to add the temperatures itself. It chose not to — it called the calculator. Why? Because we told it to in the instructions, or because we set temperature low and it learned tool use is the safer move. LLMs hallucinate math. Don't let them do math. Give them a calculator."

Writing a custom tool


from agno.tools import tool
from pathlib import Path

@tool
def save_note(filename: str, content: str) -> str:
    """Save a markdown note to disk in the notes/ folder.

    Args:
        filename: A short slug, no spaces or extension. e.g. "ai-news-jul"
        content: The full markdown content of the note.

    Returns:
        The absolute path of the file that was written.
    """
    notes_dir = Path("notes")
    notes_dir.mkdir(exist_ok=True)
    path = notes_dir / f"{filename}.md"
    path.write_text(content, encoding="utf-8")
    return str(path.resolve())
"A custom tool is a decorated function with a real docstring and real types. That's the API. You're not writing prompts — you're writing functions. Your existing Python skills transfer directly. Look at the docstring. Notice the example in the args. The model reads that. The model uses that to decide what to pass."

What the LLM actually sees


{
  "name": "save_note",
  "description": "Save a markdown note to disk in the notes/ folder.",
  "parameters": {
    "type": "object",
    "properties": {
      "filename": {
        "type": "string",
        "description": "A short slug, no spaces or extension. e.g. 'ai-news-jul'"
      },
      "content": {
        "type": "string",
        "description": "The full markdown content of the note."
      }
    },
    "required": ["filename", "content"]
  }
}
The docstring IS the API contract. Vague docstrings = vague tool use.
"This is what the model sees. Your function got translated into a JSON schema. Every word in your docstring is a hint. Every type is a constraint. If your tool keeps getting called with bad arguments, the answer is almost always: improve the docstring. Not the prompt. The docstring." Beat. "This is the single highest-leverage habit you can build tonight. Treat docstrings like they're the model's only window into your codebase. Because they are."

Three rules for great tools

  1. Verbs in the name. get_user, not user.
  2. Tight types. Use str, int, list[str], Pydantic models — not dict or Any.
  3. Docstring with examples. Tell the model when to use it AND when not to.

@tool
def lookup_invoice(invoice_id: str) -> dict:
    """Fetch an invoice by ID.

    Use this when the user asks about a specific invoice.
    Don't use this for monthly summaries — use list_invoices(month) instead.

    Args:
        invoice_id: e.g. "INV-2026-00042"
    """
    ...
"Three rules. Tape them above your monitor." "One — verbs. The model picks tools by name first, description second. `get_user` reads as an action. `user` reads as a noun. Be a verb." "Two — tight types. `dict` and `Any` are how you get hallucinated arguments at 2 AM." "Three — tell it when NOT to call. That second sentence in the docstring saves more bugs than any prompt I've ever written."

Common pitfalls

SymptomLikely cause
Tool never calledVague docstring; model doesn't know when to use it
Hallucinated args (wrong invoice ID)No examples in docstring; types too loose
Infinite loop of tool callsTool returns nothing useful; set tool_call_limit
Slow responsesTools called serially; use parallel calls when independent
Token blowupTool returns huge JSON; summarize before returning
"These are the five you'll meet in production. I've debugged all five. Tool never called is the most common — model just doesn't know it's relevant. Improve the description, problem solved.
