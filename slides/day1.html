Module 01 · 35 minutes

Fundamentals of Agentic AI

What's an agent, really? When should you build one — and when shouldn't you?

The least controversial definition

An agent is an LLM in a loop, deciding what to do next based on what it sees.

That's it. The rest is engineering.

This definition is from Anthropic's "Building Effective Agents" — it's the cleanest one out there. Resist the urge to over-define. The complexity is in the engineering, not the concept.

LLM call vs Chatbot vs Agent

LLM call

Stateless. One in, one out.


client.responses.create(
  model="gpt-4o",
  input="Hi"
)

Chatbot

Stateful conversation.
No outside actions.


agent.run("Hi")
agent.run("What did I just say?")
# remembers

Agent

Picks tools.
Loops.
Acts on the world.


agent = Agent(
  tools=[search, calc],
  ...)
agent.run("Find & sum X")

The four properties of an agent

1. Autonomy

Decides its own next step.

2. Tools

Can act on the world (search, query, write).

3. Memory

Recalls earlier turns & persistent facts.

4. Reasoning

Plans, reflects, recovers from errors.

An agentic system has all four to some degree. Workflows have only the first two and often a fixed sequence. The line is fuzzy on purpose.

The spectrum: workflow → agent

        Fixed pipeline                                     Open-ended loop
        ─────────────────────────────────────────────────────────────
        Script  →  RAG  →  Workflow  →  Agentic RAG  →  Multi-Agent
        ─────────────────────────────────────────────────────────────
        Predictable, cheap                          Powerful, expensive
        Easy to test                                Hard to test
Pick the leftmost option that solves your problem. Don't lead with "agent."

Pattern: ReAct (Reason + Act)

   ┌───────────────────────────────────────┐
   │  Thought:  I need to know X.          │
   │  Action:   search("X")                │
   │  Observ:   "X is ..."                 │
   │  Thought:  Now I can compute Y.       │
   │  Action:   calculator(...)            │
   │  Observ:   42                         │
   │  Thought:  I have the answer.         │
   │  Final:    "Y is 42"                  │
   └───────────────────────────────────────┘

Yao et al., 2022 — every modern agent uses some flavor of this.

Other patterns worth knowing

PatternWhenTrade-off
Plan-and-ExecuteMulti-step task with predictable structureBetter planning, more rigid
ReflexionAgent should self-correct after failureHigher quality, more tokens
Multi-agentDistinct roles or parallel workPowerful, very hard to debug
RoutingMany specialists, one entryClean separation, slight latency
Don't get attached to pattern names. Pick what's needed for the problem. We'll do ReAct in Lab 3 — it's the workhorse.

When NOT to use an agent

Don't

  • The flow is deterministic → use a workflow
  • You need millisecond latency
  • One LLM call already works
  • The task is safety-critical & can't tolerate hallucination

Do

  • The path branches based on intermediate results
  • You need to call out to tools to find the answer
  • The user's intent is open-ended
  • You want the system to recover from its own errors

Why Agno?

  • Pythonic — agents are just classes
  • Multi-provider — OpenAI, Anthropic, Bedrock, Gemini
  • Batteries included — memory, RAG, tools, evals
  • ~10× faster agent instantiation than LangChain

from agno.agent import Agent
from agno.models.openai import OpenAIChat

agent = Agent(
    model=OpenAIChat(id="gpt-4o-mini"),
    instructions="You are helpful.",
    markdown=True,
)
agent.print_response("Hi!", stream=True)
I'm not selling Agno — there are great alternatives (LangGraph, OpenAI Agents SDK, Pydantic AI). I picked Agno because it's the smallest amount of API surface to learn for the most ground covered.

Building AI-Powered Chatbots

From a one-shot LLM call to a chatbot with persistent memory.

What is a chat completion, really?


messages = [
    {"role": "system",    "content": "You are a polite assistant."},
    {"role": "user",      "content": "Hi, my name is Danielle."},
    {"role": "assistant", "content": "Nice to meet you, Danielle!"},
    {"role": "user",      "content": "What's my name?"},
]

# The model sees the WHOLE list every call. There's no server-side memory.
response = client.responses.create(model="gpt-4o-mini", input=messages)

"Memory" in chatbots = sending the history back every time.

The chatbot problem


agent.run("Hi, I'm Danielle.")
agent.run("What's my name?")
# → "I don't know, you didn't tell me."  😩
Each run() is a fresh API call. The agent has no memory unless we give it some.

Three flavors of memory

TypeWhat it storesLifetime
Conversation historyRecent turnsSingle session
Session storageThe full chat logAcross processes (DB)
User memoryDistilled facts about the userForever

Today we cover the first two. User memory is a Day 2 stretch goal.

Adding history


agent = Agent(
    model=OpenAIChat(id="gpt-4o-mini"),
    add_history_to_messages=True,   # 👈 include past turns
    num_history_runs=10,             # 👈 how many to include
    instructions="You are a friendly assistant.",
)

agent.run("Hi, I'm Danielle.")
agent.run("What's my name?")
# → "Your name is Danielle." ✅

The conversation is held in memory only while the process runs. Restart, lose it.

Persistent memory with SqliteStorage


from agno.agent import Agent
from agno.storage.sqlite import SqliteStorage
from agno.models.openai import OpenAIChat

storage = SqliteStorage(
    table_name="chat_sessions",
    db_file="agent_storage/chat.db",
)

agent = Agent(
    model=OpenAIChat(id="gpt-4o-mini"),
    storage=storage,
    session_id="user-42",       # same id = same chat
    add_history_to_messages=True,
)

Now restart the process. Same session_id → it picks up where it left off.

Module 03 · 55 minutes

Tools & Reasoning

Where chatbots become agents.

What is a "tool"?

A tool is a Python function the LLM is allowed to call. The model decides when, which, and with what arguments.

Under the hood: the function's signature + docstring is sent to the model as a JSON schema. The model returns a structured "call this with these args" response. The framework runs the function and feeds the result back.

The function-calling loop

   You: "What's the weather in Manila and Tokyo? Sum the temps."

       ↓

   Agent: I should call get_weather twice and add.
   → tool_call: get_weather("Manila")
   ← result: 31°C
   → tool_call: get_weather("Tokyo")
   ← result: 18°C
   → tool_call: calculator("31 + 18")
   ← result: 49
   ← Final: "49°C combined."

This is ReAct, executed for you by Agno.

Using a built-in tool


from agno.agent import Agent
from agno.models.openai import OpenAIChat
from agno.tools.duckduckgo import DuckDuckGoTools

agent = Agent(
    model=OpenAIChat(id="gpt-4o-mini"),

    show_tool_calls=True,   # 👈 see what's happening
    markdown=True,
)

agent.print_response(
    "What was the latest news about AI in the Philippines?",
    stream=True,

Writing a custom tool


from agno.tools import tool
from pathlib import Path

@tool
def save_note(filename: str, content: str) -> str:
    """Save a markdown note to disk in the notes/ folder.

    Args:
        filename: A short slug, no spaces or extension. e.g. "ai-news-jul"
        content: The full markdown content of the note.

    Returns:
        The absolute path of the file that was written.
    """
    notes_dir = Path("notes")
    notes_dir.mkdir(exist_ok=True)
    path = notes_dir / f"{filename}.md"
    path.write_text(content, encoding="utf-8")
    return str(path.resolve())

What the LLM actually sees


{
  "name": "save_note",
  "description": "Save a markdown note to disk in the notes/ folder.",
  "parameters": {
    "type": "object",
    "properties": {
      "filename": {
        "type": "string",
        "description": "A short slug, no spaces or extension. e.g. 'ai-news-jul'"
      },
      "content": {
        "type": "string",
        "description": "The full markdown content of the note."
      }
    },
    "required": ["filename", "content"]
  }
}
The docstring IS the API contract. Vague docstrings = vague tool use.

Three rules for great tools

  1. Verbs in the name. get_user, not user.
  2. Tight types. Use str, int, list[str], Pydantic models — not dict or Any.
  3. Docstring with examples. Tell the model when to use it AND when not to.

Common pitfalls

SymptomLikely cause
Tool never calledVague docstring; model doesn't know when to use it
Hallucinated args (wrong invoice ID)No examples in docstring; types too loose
Infinite loop of tool callsTool returns nothing useful; agent retries forever — set tool_call_limit
Slow responsesTools called serially. Use parallel tool calls when independent.
Token blowupTool returns huge JSON; summarize before returning
